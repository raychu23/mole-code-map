# `mole check` and questions

## How to use

```sh
mole check <sha>                     # a specific commit
mole check --diff <file> [--base SHA]  # a diff file (e.g. from `git diff > d.patch`)
mole check --worktree                # your uncommitted working-tree changes
```

For every hunk the change touches, `mole check` looks up past fixes that last wrote those exact lines (with
their commit, subject, reason, guarding tests and source) and, from those facts plus any notes on the code,
generates up to 3 questions worth asking before merging (`L3`, templated, not model-generated).

Two extra flags:
- `--spec-kit [--adr-dir DIR[,DIR]]` — also lists which decision records (from `.mole/decisions` and any
  ADR folders) this change's files fall under, with their current flag.
- `--run-tests` — delegates to `mole verify` (runs the tests whose coverage touches the changed lines; see
  `packages/verify`).

This is the exact check plugins/claude-code's Stop hook runs on your session's diff
(`plugins/claude-code/scripts/stop.mjs`), shown to you as a systemMessage — it informs, it never blocks
Claude from stopping.

## What it reads / writes

- **Reads:** git history for the given commit/diff/working tree; `.mole/notes/*` (your notes, see
  `notes-and-memory.md`); `.mole/decisions/*` when `--spec-kit` is set.
- **Writes:** nothing. `mole check` is read-only.

## Limits

- Past-fix lookup is git-blame-based: a file history rewritten (e.g. a squash-merge that drops prior
  commits) loses that history.
- Questions are templated from facts Mole already has (past fixes, notes, decision flags) — they are not
  generated by a model and will not invent context Mole doesn't hold.
- `--run-tests` selection is as good as the coverage data it was built from; an untested line has no
  guarding test to report, which `mole check` says plainly rather than guessing one.
